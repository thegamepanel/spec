# ADR-0004: Do not implement PSR-11

## Context

PSR-11 is PHP's shared container interface: `get()` and `has()`, each keyed by a string identifier. What it offers is
interchangeability. An application can swap one container for another, and a library written against the interface
works with any container that implements it.

The panel is not a framework. It is one purpose-built system distributed as a single binary. Nobody replaces its
container, and nothing outside the panel integrates with it at the level of the container.

## Decision

I will not implement PSR-11. Code that wants something from the container will describe it with the container's own
[resolution](../GLOSSARY.md#resolution) and [invocation](../GLOSSARY.md#invocation) objects rather than a string passed
to `get()`, and no part of the panel will depend on the `Psr\Container` interfaces.

## Alternatives

**Implementing PSR-11** alongside the container's own API, so that a library written against the interface could be
handed the panel's container. I rejected this because interchangeability buys nothing in a bespoke system shipped as
a single binary. The PSRs are also dated, and implementing one bends a design into its shape, where the container can
instead be shaped around what the panel needs.

Whether this was weighed at the time, or simply never adopted, is not recorded.

## Consequences

Easier:

- The container's API will follow what the panel needs. A [resolution](../GLOSSARY.md#resolution) will carry its name,
  [qualifier](../GLOSSARY.md#qualifier), arguments, and whether it is lazy or [liminal](../GLOSSARY.md#liminal) as part
  of the request, rather than packing them into a string.

Harder:

- A library that expects a PSR-11 container will not be able to use the panel's.

Constrained:

- Components will depend on the container's own API, and on nothing from PSR-11.
